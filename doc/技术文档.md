# P2PChat 技术文档

本文档描述 P2PChat 的架构设计、核心流程、数据结构与关键实现细节，供二次开发与维护参考。

## 1. 总体架构

P2PChat 是一个**纯前端应用**，由 HTML + CSS + JS 三个文件组成（`index.html` / `css/style.css` / `js/app.js`），无外部依赖、无构建步骤、无后端服务。`main` 分支保留单文件版本（CSS/JS 内联在 `index.html`），`dev` 分支为拆分后的多文件开发版。

### 1.1 技术选型

| 能力 | 方案 |
|------|------|
| 传输通道 | WebRTC 双 `DataChannel`：`"chat"`（文字+控制，有序可靠）+ `"file"`（文件/图片/视频/语音 meta/分块/结束标志，有序可靠），独立 SCTP 流互不阻塞 |
| 加密 | DTLS（WebRTC 强制，端到端） |
| 信令 | 手动复制粘贴连接码（base64 编码的 JSON） |
| NAT 穿透 | 始终启用国内公共 STUN 获取 srflx 反射地址，绕过 Chrome mDNS 混淆；host 候选作补充。仍需双方在同一局域网或均具公网 IP（STUN 不能穿越对称型 NAT，见 §1.4） |
| 持久化 | `localStorage` 自动保存 + JSON 文件导出/导入 |
| UI | 原生 DOM + 响应式 CSS（桌面双栏 / 移动单栏） |
| 二维码 | `qrcode-generator`（生成）+ `jsQR`（解析），本地库随项目分发，`file://` 离线可用 |

### 1.2 为什么是「手动信令」

浏览器安全沙箱有两点根本限制：
1. 无法用 IP 建立原始 TCP/UDP 连接；
2. 无法监听入站连接。

因此「输入 IP 即直连」在纯前端不可行。WebRTC 是唯一可行的浏览器 P2P 技术，但其建立连接需要一次信令交换（交换 SDP offer/answer）。在无后端的前提下，采用**手动复制粘贴连接码**完成信令。

### 1.3 固有限制

WebRTC 的 SDP（含 DTLS 指纹、ICE ufrag/pwd）是**每次会话临时生成**的，无法跨会话复用。因此：
- 已保存的联系人**无法凭存储的 IP 自动重连**；
- 每次重新连接仍需双方**重新交换一次连接码**。

联系人列表中的 IP/备注仅用于识别与整理，不用于「拨号」。

### 1.4 候选类型与 mDNS

ICE 连通依赖候选（candidate）：

| 候选 | 来源 | 受 mDNS 影响 |
|------|------|--------------|
| `host` | 本机网卡 IP | 是，被混淆为 `*.local` |
| `srflx` | STUN 反射地址 | 否 |
| `relay` | TURN 中继 | 否 |

仅直连模式 `iceServers: []`，ICE 只能收集 `host` 候选。Chrome 默认开启 mDNS 混淆，将 host 候选改写为 `*.local`，对端在不同子网 / 组播受限 / 不同浏览器实例时常解析失败，导致连接**静默失败**（ICE 不报错，只是连不通）。因此仅直连模式下，**关闭 mDNS 混淆是连通前提**（详见 §8）。有 STUN 时此问题不存在——`srflx` 候选为 STUN 返回的真实地址，不依赖 host，故 mDNS 开关与否均能连通。

> **STUN 辅助始终启用**：较新 Chrome 版本已收紧/移除 `chrome://flags/#enable-webrtc-hide-local-ips-with-mdns` 开关，用户可能无法手动关闭 mDNS。因此 `newPC()` 始终填入公共 STUN，ICE 即可收集 `srflx` 候选绕过 mDNS。仅在建连阶段联系 STUN 获取反射地址，消息仍端到端加密、不经过 STUN。`collectMyIps()` 探测本机地址时同样启用 STUN，以收集 `srflx` 反射地址用于本机地址面板展示（本机真实 IP 被隐藏时显示 STUN 反射的公网地址并标注）。
>
> **IPv6 srflx 兜底**：国内公共 STUN（`stun.miwifi.com` / `stun.qq.com` / `stun.chat.bilibili.com`）仅有 A 记录，只能反射 IPv4；mDNS 同样会隐藏公网 IPv6 的 host 候选，导致 IPv6 无 srflx 兜底而无法直连。为此补充 Cloudflare STUN（`stun.cloudflare.com`，有 AAAA 记录，支持 IPv6 反射且国内可达）作为首选 IPv6 候选，Google STUN（`stun.l.google.com`，同样有 AAAA）作为候补：浏览器通过 IPv6 向这些 STUN 请求可产生 IPv6 `srflx` 候选，恢复 mDNS 隐藏下的 IPv6 直连。Google STUN 国内可能不可达，不可达时退回 IPv4（国内 STUN 及 Cloudflare 仍兜底），不影响连接。WebRTC 对所有 STUN 并发请求，互不依赖。

### 1.5 ICE 选路机制

ICE（Interactive Connectivity Establishment）不是按某个固定候选连接，而是**并行尝试所有可能的路径，谁先连通就选谁**。

**优先级计算**（浏览器内置，应用层不可控）：

```
priority = type_preference × 2^24 + local_preference × 2^8 + (256 - component_ID)
```

| 因素 | 取值 |
|------|------|
| type_preference | host=126, srflx=100, relay=0 |
| local_preference | IPv6 略高于 IPv4（通常 65535 vs 65534） |
| component_ID | ICE 组件号（DataChannel 为 1） |

**选路流程**：

1. 收集阶段：ICE Agent 收集本机所有候选（各网卡 host v4/v6 + 各 STUN 返回的 srflx v4/v6）
2. 交换阶段：双方交换 SDP（含全部候选），各自生成 candidate-pair 列表
3. 检查阶段：按优先级排序后**并行**发起 STUN binding request 进行连通性检查
4. 选定阶段：最先成功握手并通过 DTLS 认证的 pair 被 nominated，其余丢弃

**典型场景**：

- 双方均有公网 IPv6 host + NAT IPv4 srflx：IPv6 host 优先级最高，先尝试，成功则直连；若不通用低优先级的 IPv4 srflx
- 双方同局域网 host + 多个 srflx：host 候选优先级最高，局域网内直连极快，srflx 作为后备不参与最终选定
- 一方有公网 IPv6、另一方仅有 IPv4 srflx：IPv6 无法配对，ICE 仅 IPv4 srflx 一条通路

**应用层获取结果**：`detectPeerIp()` 通过 `pc.getStats()` 读取 `selected` 为 true 的 candidate-pair，拿到实际使用的对端地址和候选类型，用于 UI 显示（IP / 连接模式标签）。选路过程本身完全由浏览器 ICE 引擎自动完成。

## 2. 连接流程（三步手动信令）

为简化交互，**关闭 trickle ICE**，等 ICE 收集完成后读取完整 `localDescription`（含全部候选）再编码，使每方只需复制一段文本。

> **生成连接码的等待提示**：启用 STUN 后，`waitIceComplete` 需等 STUN 服务器返回 `srflx` 候选（网络往返），生成邀请码/应答码会有短暂延迟。`startInvite` 点击后立即弹出对话框显示 spinner +「正在生成邀请码…」；`acceptOffer` 点击后立即在应答码框显示「正在生成应答码…」并 toast。避免用户以为点击无反应。`ips` 字段改用 `extractIpsFromPc(pc)` 复用已收集候选，省去额外的 STUN 探测往返。

```
邀请方 A                         被邀方 B
─────────                       ─────────
createDataChannel('chat')       ondatachannel 按 label 分发
createDataChannel('file')       'chat' → 登记身份
                                'file' → 编入 connections
createOffer + setLocalDescription
wait iceGatheringState==='complete'
生成【邀请码】 ────────────────▶ 粘贴邀请码
                                  setRemoteDescription(offer)
                                  createAnswer + setLocalDescription
                                  wait ICE complete
                  ◀────────────  生成【应答码】
粘贴应答码
setRemoteDescription(answer)
                ▼ ICE 连通 / DTLS 握手 ▼
        双 DataChannel open，互发 hello
       'chat' 通道登记身份 → finalizeChannels
                ▼ 双向加密聊天 ▼
```

### 连接码格式

```
前缀 + base64( payload )
```

v2.8.0 起连接码经 **deflate-raw 压缩**缩短约 60%（SDP 高度重复，压缩率高）：

| 前缀 | payload | 说明 |
|------|---------|------|
| `z` | base64( deflate-raw( JSON ) ) | 新版默认，压缩 |
| `b` | base64( JSON ) | 旧浏览器无 `CompressionStream` 时回退 |
| 无 | base64( JSON ) | 旧版（v2.7.x 及以前）连接码 |

JSON 结构：

- `type`：`'offer'` 或 `'answer'`
- `sdp`：`RTCSessionDescription`（含所有 ICE 候选）
- `identity`：`{ id, name }`，本机身份
- `ips`：本机真实 IP 字符串数组（host v4/v6 + STUN srflx 反射地址，排除 `*.local`/`0.0.0.0`/`::`），由 `extractIpsFromPc(pc)` 从已收集的 `localDescription` 提取（复用握手 PC 候选，省一次 STUN 往返）。用于对端在 mDNS 混淆下 `getStats()` 仅拿到 `*.local` 时回退显示真实 IP（`ipType='signal'`）。**不参与连通性**（在 non-trickle 全候选架构下，真实候选 SDP 已含，故不做候选注入）。

`encodeSignal`/`decodeSignal` 为异步：编码用 `CompressionStream('deflate-raw')` 压缩 UTF-8 字节流，`bytesToB64` 转 base64 加 `z` 前缀；解码按前缀分发，`z` 用 `DecompressionStream('deflate-raw')` 解压，`b`/无前缀走原 `atob` 路径（向后兼容旧版连接码）。`typeof CompressionStream === 'undefined'` 时编码回退 `b` 前缀。UTF-8 中文兼容：压缩前用 `TextEncoder`，解压后用 `TextDecoder`；未压缩路径仍用 `btoa(unescape(encodeURIComponent(...)))`。

### 身份解析时机

- **被邀方**：邀请码中已含邀请方 `identity`，`ondatachannel` 时按 `channel.label` 分发——`'chat'` 通道传入 `knownPeerId` 即刻登记身份，`'file'` 通道挂靠同一 `pc` 等后续补连。
- **邀请方**：应答码中虽含被邀方身份，但邀请方在 `finalizeOffer` 阶段未解析它；邀请方需等对端通过 `'chat'` DataChannel 发来 `hello` 消息才能确认身份。故邀请方 chat 通道打开后先「等待对端身份」，收到 `hello` 再调用 `finalizeChannels()`。
- **file 通道补连**：若 chat 先于 file 打开，`finalizeChannels` 建立连接时 `connections.file` 暂为 `null`；file 通道打开后，`onChannelOpen` 的 file 分支查找同 PC 的 chat 连接，自动补连 `conn.file = channel`。反之亦然——无论两个通道哪个先到，最终均正确配对。

## 3. 数据结构

### 3.1 持久化结构（`localStorage` key: `ipvchat_data`）

```js
{
  version: 4,
  identity: { id, name },                 // 本机身份
  contacts: [
    { id, name, peerName, ip, ipType, lastSeen, note, nameSet, peerIps?, peerDeliveredSeq?, peerReadSeq?, peerDeliveredTs?, peerReadTs?, lastReadTs? }
  ],
  messages: { [contactId]: [ { ts, dir, text, seq? } | { ts, dir, file:{fid,name,size} } | { ts, dir, image:{iid,name,size} } | { ts, dir:'sys', text } ] },
  settings: {},                            // STUN 始终启用，无运行时开关
  unread: { [contactId]: number }          // 未读消息计数
}
```

字段说明：
- `identity.id`：随机生成的本机唯一标识，随连接码发送给对端，作为联系人去重键。
- `contacts[].id`：对端身份 id（非 IP），用于匹配连接。
- `contacts[].peerName`：对端账号用户名，每次连接经 `hello` 同步更新。
- `contacts[].name`：本机自定义备注名（仅 `nameSet=true` 时有效）。
- `contacts[].nameSet`：是否已设置备注；为 `true` 时显示为「备注（用户名）」，否则显示用户名。
- `contacts[].peerIps`：对端信令携带的真实 IP 数组（连接建立时写入）；`detectPeerIp` 在 `getStats()` 拿到 `*.local`/空时回退用它显示，并置 `ipType='signal'`。
- `contacts[].peerDeliveredTs`：对端浏览器最后确认「已送达」的时间戳（收到 `{type:"ack"}` 时更新）。仅用于文件/图片消息回退判断（文字消息用 seq 精确判断）。
- `contacts[].peerReadTs`：对端浏览器最后确认「已读」的时间戳（收到 `{type:"read"` 时更新）。仅用于文件/图片消息回退判断。
- `contacts[].peerDeliveredSeq`：对端 ACK 累积确认的最大 seq（收到 `{type:"ack", seq}` 时 `Math.max` 更新，默认 -1）。文字消息据此精确判断「✓已送达」，替代旧版时间戳近似。
- `contacts[].peerReadSeq`：对端已读的最大 seq（收到 `{type:"read", seq}` 时 `Math.max` 更新，默认 -1）。文字消息据此精确判断「✓已读」。
- `contacts[].lastReadTs`：本机用户上次进入该联系人聊天界面的时间戳（`selectContact` 时记录），用于渲染「── 以下为新消息 ──」分界线。
- `contacts[].ipType`：对端地址来源，`host`/`prflx`（直连）/`srflx`（STUN 辅助）/`signal`（信令回退）。
- `messages[].dir`：`'in'` / `'out'` / `'sys'`（系统提示）；消息体为 `text`（文字）、`file`（文件元数据）或 `image`（图片元数据）。
- `messages[].seq`：可选 number，文字消息的序列号（`sendMsg`/`flushPendingMessages` 发送时分配并持久化）。用于精确回执判断；文件/图片消息无 seq，回退时间戳。
- `messages[].pending`：可选 bool，`true` 表示离线消息，等待连接恢复后通过 `flushPendingMessages` 发出。
- `messages[].file`：文件消息元数据 `{fid,name,size}`，**不含文件内容**。
- `messages[].image`：图片消息元数据 `{iid,name,size}`，**不含图片内容**。
- `unread`：各联系人未读消息数；选中该联系人时清零。
- `settings`：v4 起仅直连模式；STUN 辅助现始终启用（代码常量 `DEFAULT_STUN_SERVERS`），无运行时开关，历史 `stunEnabled`/`stunUserSet` 字段已弃用忽略。

### 3.2 运行时状态（非持久化）

| 变量 | 说明 |
|------|------|
| `store` | 加载自 localStorage 的全局数据对象 |
| `currentId` | 当前选中联系人 id |
| `pendingPC` | 握手中的 `RTCPeerConnection` |
| `pendingPeerIps` | 解析对端连接码时暂存其真实 IP（`finalizeChannel` 写入 `contact.peerIps` 后清空） |
| `connections` | `Map<contactId, {chat, file, pc, outSeq, inSeq, pending}>`，双通道连接对象。`chat` 为文字+控制 DataChannel，`file` 为文件/图片数据 DataChannel；`outSeq` 为本方下一条发出消息序列号，`inSeq` 为期望收到的下一个序列号；`pending` 为待 ACK 确认消息的重传队列 `Map<seq, {text, ts, timer, retries}>`。**v2.7.8 起**，`finalizeChannels` 建连时 `outSeq`/`inSeq` 不再归零，而是从 `store.messages` 历史消息的 max seq + 1 恢复——避免重连后 seq 归零与持久化的 `peerReadSeq`/`peerDeliveredSeq` 错位（导致发送即误判已读）及跨连接重复消息无法去重 |
| `channelMap` | `Map<channel, {pc, contactId|null, isChat, incomingFile?, incomingImage?, incomingVideo?, incomingAudio?}>`，通道→连接信息反查。`isChat` 区分 chat/file 通道 |
| `fileTransfers` | `Map<fid, {received,size,dir,contactId,name}>`，文件传输进度（出/入共用） |
| `imageTransfers` | `Map<iid, {received,size,dir,contactId,name}>`，图片传输进度（出/入共用） |
| `fileUrls` | `Map<fid, objectURL>`，接收文件下载链接（运行时，不持久化） |
| `imageUrls` | `Map<iid, objectURL>`，接收图片缩略图链接（运行时，不持久化） |
| `revivable` / `autoReviveTimers` / `autoReviveRetries` | 断线恢复：存活 PC 缓存 / 自动恢复定时器 / 恢复重试次数（v2.11.0） |
| `onboarding` / `exitAllowed` | 引导态标志 / 退出确认放行标志 |

## 4. 模块设计

### 4.1 WebRTC 层

- `newPC()`：创建 `RTCPeerConnection`，`iceServers` 始终填入 `DEFAULT_STUN_SERVERS`（国内公共 STUN + Cloudflare STUN / Google STUN 补充 IPv6），收集 `srflx` 候选绕过 mDNS。默认 `ondatachannel` 按 `e.channel.label` 判断 `isChat`。
- `waitIceComplete(pc)`：Promise，等 `iceGatheringState==='complete'`，带 5 秒兜底超时。
- `bindChannel(channel, pc, knownPeerId, knownPeerName, isChat)`：绑定通道事件（open/message/close/error）；ICE 状态监听仅由 `isChat=true` 的通道绑定，避免 file 通道重复触发。
- `finalizeChannels(chatCh, peerId, peerName)`：身份确认后，查找同 PC 的 file 通道，将双通道登记到 `connections`（`{chat, file, pc, outSeq, inSeq, pending, hbTimer}`）。继承旧 `finalizeChannel` 逻辑：创建/匹配联系人、写入 `peerIps`、探测对端 IP、切换 UI。**v2.7.8 起** `outSeq`/`inSeq` 从历史消息 max seq + 1 恢复（见 §4.2）。**v2.11.0 起**清零 `autoReviveRetries` 并 `startHeartbeat` 启动心跳保活。末尾自动调用 `flushPendingMessages(peerId)` 发送离线期间排队的消息。
- `flushPendingMessages(contactId)`：遍历 `store.messages[contactId]` 中所有 `pending:true` 的发出消息，逐条通过 chat 通道发送并加入 ACK 重传队列，持久化 `seq` 后删除 `pending` 标记，保存 + 重新渲染。
- `addPendingMessage(contactId, dir, text, ts)`：离线发送时写入带 `pending:true` 的消息并渲染。
- `detectPeerIp(pc, contactId)`：通过 `pc.getStats()` 读取选中的 candidate-pair 解析对端地址；若为 `*.local`/空则回退用 `contact.peerIps` 并置 `ipType='signal'`。
- `connectDiagnose(pc)`：STUN 始终启用，根据 `hasRealHostCandidate(pc)` / 对端 IP 返回场景化诊断文案，供连接看门狗超时提示。
- `startConnectWatchdog(pc, label)`：真正开始 ICE 连通后（邀请方 `finalizeOffer` 提交应答码 / 被邀方 `acceptOffer` 生成应答码）90s 未建连则 toast 诊断。**v2.7.9 起**两处修正：①邀请方生成邀请码阶段**不再**启动看门狗——此时仍在等对方人工回发应答码，交换时间不可控，旧版把它误算进连通超时，导致公网 IPv6 场景下人工往返超 20s 后 `pendingPC` 被清理，A 粘贴应答码时报「连接已取消，请重新开始」；②超时由 20s 延长至 40s。**v2.10.0 起再延长至 90s**——覆盖双方交换连接码/二维码（扫码、复制粘贴）+ 跨网络 IPv6 ICE 连通的总耗时，提升容错；ICE `failed` 事件会立即报错，看门狗仅在 ICE 卡住（不 failed 也不 connected）时兜底，延长不影响真正失败的及时反馈。超时后清理资源：若 `pendingPC===pc` 调 `cleanupPending()`，否则单 `pc.close()`，避免握手 PC 残留。
- `cleanupPending()`：清理 `pendingPC` 上的所有通道与 PC、清空 `pendingChannel`/`pendingPeerIps`、关看门狗。`cancelConnect` 与下次建连前调用。
- `onChannelClose(channel)`：断开当前通道；**双通道都断**才 `delete connections`，清理 pending 定时器与心跳（`stopHeartbeat`，v2.11.0），存活 PC 迁入 `revivable` 供免交换码恢复。
- `deleteContact()`：删除联系人前关闭 `connections` 的 PC 与 `revivable` 中残留的 PC（v2.7.6），防止 ICE 连接泄漏。

### 4.2 消息协议（双 DataChannel：chat 承载控制流，file 承载数据流）

v2.6 起拆分为两个独立 DataChannel，消除队头阻塞（head-of-line blocking）：

| 通道 | label | 用途 | SCTP 配置 |
|------|-------|------|-----------|
| chat | `"chat"` | JSON 控制消息（文字、回执、hello、bye） | `ordered:true` |
| file | `"file"` | 文件/图片/视频/语音的 `meta`/二进制分块/`end`（全周期） | `ordered:true` |

JSON 控制消息类型：

| type | 字段 | 说明 |
|------|------|------|
| `hello` | `identity` | 连接建立后互发，交换身份；已连接时再次发送表示**改名同步**（对端仅更新 `peerName`，不重走连接流程） |
| `msg` | `ts, text, seq` | 聊天消息；v2.6 新增 `seq`（自增序号），用于 ACK 确认和重传追踪 |
| `file-meta` | `fid, name, size, mime` | 文件传输开始，声明元数据（走 file 通道） |
| `file-end` | `fid` | 文件传输结束，接收方组装 Blob（走 file 通道） |
| `image-meta` | `iid, name, size, mime` | 图片传输开始，声明元数据（走 file 通道） |
| `image-end` | `iid` | 图片传输结束，接收方组装 Blob 并渲染缩略图（走 file 通道） |
| `video-meta` | `vid, name, size, mime` | 视频传输开始，声明元数据（v2.12.0，走 file 通道） |
| `video-end` | `vid` | 视频传输结束，接收方组装 Blob 并渲染内嵌播放器（v2.12.0，走 file 通道） |
| `audio-meta` | `aid, name, size, mime` | 语音传输开始，声明元数据（v2.13.0，走 file 通道） |
| `audio-end` | `aid` | 语音传输结束，接收方组装 Blob 并渲染内嵌播放器（v2.13.0，走 file 通道） |
| `ack` | `seq` | **累积确认**：对端已收到 seq 及之前所有文字消息。发送方据此清除 pending 队列并更新 `peerDeliveredSeq` |
| `delivered` | `ts` | （旧版兼容）已送达回执：timestamp 阈值式。新版仍处理此消息以兼容旧版对端，但不再主动发送 |
| `read` | `ts, seq?` | 已读回执：对端选中该联系人聊天时回复。`seq` 为对端已收到的最大 seq（`inSeq-1`），发送方据此更新 `peerReadSeq`；无 seq 时回退时间戳 |
| `bye` | — | 主动断开通知 |
| `ping` | `ts` | 心跳探测（v2.11.0，走 chat 通道），收到立即回 `pong`；激活 ICE keepalive、探测存活，不参与 ACK/回执 |
| `pong` | `ts` | 心跳回应（v2.11.0），连接存活确认 |

二进制分块（走 file 通道）：ArrayBuffer，16KB/块。**v2.10.2 起 `meta`/分块/`end` 全部走同一 `"file"` 通道**（同一 SCTP ordered stream），保证 `end` 严格在所有分块之后到达。`file-meta`/`image-meta` 声明元数据后在 `"file"` 通道上连续发送块，`file-end`/`image-end` 在同一 `"file"` 通道标志结束。因 meta 与分块同在 file 通道的 `channelMap` 条目，`onChannelMsg` 二进制分支优先取本通道条目的 `incomingFile`/`incomingImage`；为兼容旧版对端（meta 仍走 chat 通道），未找到时仍回溯同 PC 的 chat 条目查找累积缓冲区。身份未确认（`contactId` 为 null）前，业务消息被丢弃。

**消息可靠传输（ACK + 重传）**：

文字消息带 `seq` 自增序号。接收方收到后立即在 chat 通道回复 `{type:"ack", seq:N}`（累积确认，N 为当前已收到的最大 seq）。发送方维护 `connections[contactId].pending` Map：

```
pending: Map<seq, {text, ts, timer, retries}>
```

- **去重**（v2.7.6）：接收方先判断 `m.seq < conn.inSeq`，已处理过的消息只回累积 ACK、不重复 `addMessage`，避免弱网重传导致重复气泡
- 消息发送后 3s 未收到 ACK → 重传，指数退避：3s → 6s → 12s
- 最多重试 3 次（v2.7.6 修正时序：先 `++retries` 再判断 `>=3`，总延迟 ~21s 而非旧版 ~45s），仍无 ACK 则放弃 + 显示 ⚠ 系统提示
- `retransmitMsg` 顶部检查 `conn.chat` 非空（v2.7.6），chat 通道先断时停止重传，避免 TypeError 空转
- `sendMsg()` 在 chat 通道 `bufferedAmount > 64KB` 时拒绝发送（toast"网络拥塞"），防止静默丢弃
- file-meta/image-meta/file-end/image-end 复用旧版 `delivered` timestamp 回执（无 seq）

**已读/已送达回执精确化（v2.7.6）**：`refreshMessageReadStatus` 对文字消息用 seq 判断——`msg.seq <= peerReadSeq` 标「✓已读」，`<= peerDeliveredSeq` 标「✓已送达」；文件/图片消息无 seq，回退时间戳判断（`ts <= peerReadTs`/`peerDeliveredTs`）。`read` 在 `selectContact` 或 `onChannelMsg` 收到 msg/file-meta/image-meta（当前正选中该联系人）时发送，附带 `seq=inSeq-1`。收到回执后通过 `requestAnimationFrame(()=>refreshMessageReadStatus(...))` 延迟到下一渲染帧更新 DOM，避免与 `renderMessages` 的 `innerHTML` 重建竞争。显示优先级：已读 > 已送达。刷新页面后回执状态清除。

**重连 seq 基线恢复（v2.7.8）**：`finalizeChannels` 建连时 `outSeq`/`inSeq` 从 `store.messages` 历史 max seq + 1 恢复（不归零）。因 `peerReadSeq`/`peerDeliveredSeq` 持久化在 contact 不随连接重置，若 `outSeq` 归零会导致新发出 seq 0 ≤ 旧 `peerReadSeq` 误判「已读」，且 `inSeq` 归零导致跨连接重复消息无法去重。恢复基线后新发出 seq 必然 > 旧 `peerReadSeq`，回执判断正确。

### 4.4 本机地址探测

`collectMyIps()`：核心收集函数，创建临时 `RTCPeerConnection`（启用 `DEFAULT_STUN_SERVERS`），收集候选返回 `{host4,host6,mdns,srflx}`。

`fe80::` 开头标注「链路本地」。仅显示本机地址。

### 4.6 文件、图片与视频传输

**单通道全周期（v2.10.2）**：文件/图片的 `meta`/二进制分块/`end` 全部走同一 `"file"` DataChannel（同一 SCTP ordered stream），保证 `end` 严格在所有分块之后到达。文字消息和回执走独立的 `"chat"` 通道，两条 SCTP 流互不阻塞，传输大文件时文字消息不被卡在队列后面。

> **为何不全走 chat 通道**：v2.7.6 曾把 meta/end 放 chat、分块放 file，理由是避免 file 通道队头阻塞拖慢 end。但 SCTP 仅保证**单 stream 内有序**，**跨 stream 无序**——公网高延迟/抖动下，chat 通道的 `end`（小消息、缓冲空、立即发出）会先于 file 通道尾部分块（缓冲高达 8MB、缓慢发送）到达对端，导致接收方用不完整 chunks 拼 Blob，图片出现「顶部一条/侧边一条/灰色条带」等残缺，且 `incomingImage` 被置 null 后迟到的分块被丢弃。改回同一 file 通道后，ordered 保证 meta → 分块 → end 严格顺序，根治残缺。

**文件传输**（📎）：
- `sendFile(file)`：`file-meta`（file 通道）→ 按 16KB `file.slice().arrayBuffer()` 分块通过 `conn.file` 发送 → `file-end`（file 通道，同一 ordered stream）。`conn.file.bufferedAmount` 超 8MB 时经 `backpressureWait()` 做背压。v2.7.6 起 while 循环条件含 `channel.readyState==='open'`，背压等待带 30s 超时 + close/error 事件兜底（`backpressureWait`），通道断开时函数正常退出而非永久卡死。v2.10.2 起用 `acquireFileLock()` 串行化，同一 file 通道同一时刻只跑一个传输，防止并发分块交错。
- `startReceiveFile()` / `finishReceiveFile()`：在 `channelMap` 条目的 `incomingFile` 上累积分块，完成后 `new Blob(chunks)` 生成 objectURL 存入 `fileUrls`。v2.10.2 起 meta 走 file 通道，`incomingFile` 直接挂在本通道条目；为兼容旧版对端（meta 走 chat），`onChannelMsg` 二进制分支在本条目未找到时仍回溯同 PC 的 chat 条目。
- `renderFileCardInto()` / `updateFileProgress()`：文件卡片实时渲染进度条；传输中显示百分比，完成后接收方显示「下载」、发送方显示「已发送」。

**图片传输**（🖼 / 📷）：
- `sendImage(file)`：验证 `file.type.startsWith('image/')`，`image-meta`（file 通道）→ 分块通过 `conn.file` 发送 → `image-end`（file 通道，同一 ordered stream）。发送方立即 `URL.createObjectURL(file)` 存入 `imageUrls` 显示缩略图预览。复用文件传输的分块常量、背压机制与 `acquireFileLock()` 串行锁（v2.10.2 同 `sendFile`）。
- **拍照发送**（v2.10.0）：`pickCamera()` 触发隐藏 `<input type=file accept="image/*" capture="environment">`（`#cameraInput`），移动端直接调起后置摄像头拍照，拍完走同一 `sendImage` 流程；桌面浏览器忽略 `capture` 退回文件选择。「🖼」从相册/文件选图（无 `capture`）。
- `startReceiveImage()` / `finishReceiveImage()`：同文件模式，写入 `incomingImage`，完成后 `new Blob(chunks)` 生成 objectURL 存入 `imageUrls`。v2.10.2 同样优先取本通道条目，回溯 chat 条目作旧版兼容。
- `renderImageInto()`：渲染 `<img>` 缩略图（max-height 360px），点击调 `openImageview(src)` 打开**页内图片查看器**（v2.12.1，替代旧版 `window.open`——iOS 不响应、安卓/PC 开新标签页）。查看器支持按钮 +/−/重置缩放、双击切换 1x/2.5x、滚轮缩放（PC）、双指 pinch 缩放（移动端，v2.12.3）、放大后拖动平移（鼠标/单指）、点背景或叉号关闭。v2.12.2 修复拖动后合成 click 误关闭（`ivMoved` 标志 + 延迟关闭）。v2.12.3 修复移动端工具栏不显示（toolbar 改 flex 子项置底、`max-height:80vh` 留空间，弃用 `position:fixed`）并新增双指 pinch 缩放。传输中显示 spinner + 百分比；失效显示占位提示。

**视频传输**（🎬 / 🎥，v2.12.0）：
- `sendVideo(file)`：验证 `file.type.startsWith('video/')`，`video-meta`（file 通道）→ 16KB 分块通过 `conn.file` 发送 → `video-end`（file 通道，同一 ordered stream）。结构与 `sendImage` 完全对称，复用 `acquireFileLock()` 串行锁与背压机制。发送方立即 `URL.createObjectURL(file)` 存入 `videoUrls` 预览。
- **录像发送**：`pickVideoCamera()` 触发隐藏 `<input type=file accept="video/*" capture="environment">`（`#videoCameraInput`），移动端调起后置相机录像；`pickVideo()` 从本地选视频（无 `capture`）。桌面浏览器忽略 `capture`。**v2.12.4 起 iOS 下运行时移除 `capture`**——iOS Safari 的 `capture` 直接调起相机录像会使 Safari 后台，叠加已有 WebRTC 连接的内存占用，触发系统回收导致整个浏览器闪退；改走系统选择器（用户仍可选「录像」），Safari 不立即后台。`sendVideo` 拒绝 >100MB 视频，防接收端拼 Blob 内存溢出。
- `startReceiveVideo()` / `finishReceiveVideo()`：同图片模式，写入 `incomingVideo`，完成后 `new Blob(chunks)` 生成 objectURL 存入 `videoUrls`。
- `renderVideoInto()`：渲染 `<video controls preload="metadata">` 内嵌播放器（`max-width:min(72vw,300px)`、`max-height:300px`，v2.12.1 收紧尺寸避免安卓端排版过大）；传输中显示 spinner + 百分比；失效显示占位提示。

**语音消息**（🎤，v2.13.0）：
- **按住录音**：composer 输入框左侧话筒按钮（SVG 图标），`mousedown`/`touchstart` 调 `startRecord()` → `getUserMedia({audio:true})` + `MediaRecorder` 开始录音，显示 `.rec-indicator` 浮层（红点脉动 + 计时 + 「松手结束」）；`mouseup`/`touchend` 调 `stopRecord()` 停止。检测 `MediaRecorder` 兼容性与连接状态（未连接 toast 提示）。MIME 优先 `audio/webm`，回退 `audio/mp4`。**v2.13.1 起优化权限体验**：①缓存 `MediaStream` 复用——松手后 10s 内再按住直接录音，免重新 `getUserMedia`（`scheduleRecRelease` 延迟释放，灭指示灯）；②权限申请期间松手不再取消，申请成功后若已松手则 toast「麦克风已就绪，请按住话筒录音」并保留 stream，避免「同意后还要再按一次」。页面卸载/退出账号释放 stream。**v2.13.2 起**：`startRecord` 立即显示录音指示（"准备中…"）；`start(250)` timeslice 分段触发 + `onerror` 处理。**v2.13.3 起**：①iOS Safari 的 `MediaRecorder` 录音会触发进程级崩溃（无法 try/catch 兜底），检测 iOS 后禁用录音并 toast 提示改用 Edge/Chrome 或电脑端；②回放 Blob type 用 `mediaRecorder.mimeType`（实际产出格式）替代检测值，修复 Edge 回放「格式错误」；③`recPreview` 加 `error` 事件提示。
- **录音确认弹窗**（`dlgAudioConfirm`）：录音停止后弹出，含 `<audio controls>` 回放预览 + 「取消」（`cancelRecordedAudio` 丢弃）/「发送」（`sendRecordedAudio` 调 `sendAudio`）。
- `sendAudio(blob)`：`audio-meta`（file 通道）→ 16KB 分块通过 `conn.file` 发送 → `audio-end`（file 通道，同一 ordered stream）。结构与 `sendImage`/`sendVideo` 完全对称，复用 `acquireFileLock()` 串行锁与背压机制。发送方立即 `URL.createObjectURL(blob)` 存入 `audioUrls` 显示播放器。
- `startReceiveAudio()` / `finishReceiveAudio()`：同视频模式，写入 `incomingAudio`，完成后 `new Blob(chunks)` 生成 objectURL 存入 `audioUrls`。
- `renderAudioInto()`：渲染**自定义语音气泡**（v2.13.2，替代原生 `<audio controls>`）——圆形播放按钮 + 可点击进度条 + 时长，`toggleAudioPlay` 切换播放/暂停、`seekAudio` 点击定位、`audioPlayers` Map 缓存 HTMLAudioElement；传输中显示 spinner + 百分比；失效显示占位。接收方点击播放按钮收听。

**附件聚合菜单**（v2.12.0）：composer 的 📷/🖼/📎 三按钮聚合为单个「＋」按钮（`#btnAttach`，v2.12.1 起用 SVG 图标替代全角字符「＋」，修复安卓端显示异常），点击 `toggleAttachMenu()` 弹出 `.attach-pop` 菜单（拍照 / 图片 / 视频 / 录像 / 文件）。选中任一项或点击外部自动关闭（`closeAttachMenu`）。`renderTopbar` 随连接状态启停 `#btnAttach`（替代旧的三按钮）。v2.12.5 起未连接时 `#btnAttach` 保持可点击，`toggleAttachMenu` 检测到未连接则 toast「未连接，无法发送图片/视频/文件，请先重连」并阻止菜单打开（附件需 file 通道，不支持离线发送），无联系人时提示先选择联系人。

**共用机制**：
- **内容仅存内存**：`fileUrls` / `imageUrls` / `videoUrls` / `audioUrls` 的 Blob 不持久化，刷新后失效；`store.messages` 仅存 `{fid/iid/vid/aid,name,size}` 元数据。
- **独立协议**：文件/图片/视频/语音各有独立的 meta/end 类型（`file-meta`/`image-meta`/`video-meta`/`audio-meta`），v2.10.2 起 meta/分块/end 全走 file 通道（同 SCTP ordered stream），文字/回执走 chat 通道，两条流互不阻塞。
- **接收进度同步**（v2.12.1 修复）：二进制分块到达时更新 `incomingXxx.received`，并同步写入 `fileTransfers`/`imageTransfers`/`videoTransfers`/`audioTransfers` 的 `received`，供 `updateXxxProgress` 读取渲染。旧版仅更新 `incomingXxx.received` 而 `updateXxxProgress` 读 transfers Map 的 `received`（恒为 0），导致接收方进度条始终 0%。

### 4.7 离线消息队列与消息分界线

v2.7 新增，解决「断线后无法输入」和「回到聊天难以定位新消息」的痛点。

**离线发送流程**：

1. 断线时 `renderTopbar` 保持 textarea 可用（`disabled=false`），文件/图片按钮仍禁用（无 file 通道）
2. `sendMsg` 检测 `!online` → 调用 `addPendingMessage` 写入 `{pending:true}` 的消息
3. 消息在 UI 中显示「⏳ 未发送」标记（`.read-tag.pending`，警告色）
4. 连接建立时 `finalizeChannels` → `flushPendingMessages` 逐条按 `seq` 发送并加入 ACK 队列，删除 `pending` 标记后重新渲染

**消息分界线**：

- `selectContact` 记录 `contacts[].lastReadTs = nowTs()`
- `renderMessages` 遍历消息时，若 `m.dir==='in' && m.ts > lastReadTs`，在当前消息前插入 `<div class="msg-divider">── 以下为新消息 ──</div>`
- 分界线仅显示一次（`dividerShown` 标志位），CSS 为居中半透明文本
- 离开聊天再回来时 `lastReadTs` 更新，分界线位置随之刷新

### 4.8 二维码连接（v2.9.0）

为免去手动复制粘贴长连接码，v2.9.0 新增二维码生成与扫描。引入**本地库** `lib/qrcode-generator.js`（生成）与 `lib/jsQR.min.js`（解析），随项目分发、`file://` 离线可用，不依赖 CDN。

**生成**（邀请方邀请码 / 被邀方应答码）：`showQrCode(text, title)` 用 `qrcode(0,'L')`（typeNumber=0 自动选最小版本，**纠错级 L**）生成，`qrToCanvas` 渲染到 canvas（cell=8px/模块，margin=4 模块静默区）。v2.8.0 压缩后连接码约 800 字符，对应 QR 版本 ~20（97×97 模块）。v2.9.2 起纠错级由 M 降为 L——屏幕显示的二维码无污损，L 级（7% 纠错）模块数最少（M 级为 109×109），每块显示更大，摄像头像素不足或距离较远时更易识别；旧浏览器回退未压缩码过长（>2000 字符）时 `addData/make` 抛错，catch 后 toast 提示改用文本复制。

**展示弹窗**（`dlgQr`）三个动作：
- 🔍 放大（`openQrLarge`）：`imageSmoothingEnabled=false` 最近邻缩放到约 720px 宽，保持模块清晰边界，方便远距离扫描或截图（`dlgQrLarge` 弹窗）。
- 💾 保存（`saveQr`）：`canvas.toBlob` → `<a download>` 下载 `p2pchat-qrcode.png`。
- 📤 分享（`shareQr`）：`navigator.share({files:[File]})` 调用系统 Web Share API 分享到社交 app；`navigator.canShare` 先检测图片分享能力，不支持或无 `navigator.share` 时回退保存图片。

**扫描**（v2.9.3 起拆分为两个独立入口，不再混合弹窗；v2.10.1 起优化识别成功率）：
- **相机扫码**（`showQrScanner(callback)`，弹窗 `dlgScan` 纯摄像头预览）：`getUserMedia({video:{facingMode:'environment', width:{ideal:1280}, height:{ideal:720}}})` 优先后置摄像头并限制理想分辨率避免过高拖慢；`scanLoop` 用 `requestAnimationFrame` 抓帧 → **降采样至 640 宽**（`drawImage` 缩放）→ `getImageData` → `jsQR(data,w,h,{inversionAttempts:'attemptBoth'})` 解析，命中即 `closeScanner` + 回调。降采样让 jsQR 单帧解析更快、帧率更高、单位时间内尝试次数更多，实际命中率提升。弹窗内置居中扫描框（`.scan-frame` + 动画扫描线 + 外围半透明遮罩）引导对准。摄像头不可用时状态栏提示改用「上传二维码」。
- **上传二维码**（`uploadQrTo(id)`，无弹窗）：直接触发隐藏 `<input type=file accept=image/*>`（`#scanFileInput`，置于 body）→ `Image` → `decodeQrImage` **多尺度解析**（依次 640 快扫 → 1280 细节 → 2000 高清，任一命中即返回，覆盖大图细节与小图清晰度），成功填入 textarea 并 toast，失败 toast 提示。选完文件立即 toast「正在识别二维码，请稍候…」（6s），避免图片加载/解析期间无反馈被误判卡死，结果出来后覆盖。
- `closeScanner`：`getTracks().stop()` 释放摄像头、`cancelAnimationFrame` 停帧循环、清 `video.srcObject`。

**集成点**（连接向导）：邀请方第 1 步「📱 二维码」生成邀请码 QR；邀请方第 3 步「📷 相机扫码」`scanTo('codeIn')` + 「📁 上传二维码」`uploadQrTo('codeIn')`；被邀方第 1 步同样两个入口；被邀方第 2 步「📱 二维码」生成应答码 QR。识别成功后填入对应 textarea 并 toast。连接成功时 `finalizeChannels` 自动关闭二维码展示弹窗（`dlgQr`/`dlgQrLarge`），被邀方无需手动关闭应答码二维码。

> 移动端兼容：`getUserMedia` / `navigator.share` 需 HTTPS 或 `localhost`（`file://` 下可能受限），桌面 `file://` 打开时摄像头分享可能不可用，会自动降级提示。

### 4.9 连接保活与后台恢复（v2.11.0）

针对 **iOS 墓碑机制**（后台冻结 JS、暂停 ICE keepalive）与**安卓息屏**后切回页面断链的体验优化。前提：网络未变、IP 未变、页面未被系统回收，仅后台冻结再恢复——底层 ICE 连接通常仍可恢复，需主动探测而非误判断开。

**应用层心跳**（`ping`/`pong`）：
- `finalizeChannels` 建连后 `startHeartbeat(cId)` 启动 `setInterval`，每 `HEARTBEAT_INTERVAL`（12s）经 chat 通道发 `{type:"ping"}`；对端收到立即回 `{type:"pong"}`。
- 作用：①周期数据传输防止 NAT 映射超时；②激活 ICE keepalive；③作活性探测。ping/pong 不参与 ACK/回执（`onChannelMsg` 的 delivered 逻辑已排除），旧版对端收到 ping 仅回退发 `delivered`，无副作用。
- `onChannelClose`/`deleteContact`/`doLogout`/`importJSON` 均调用 `stopHeartbeat(conn)` 清理定时器。

**visibilitychange 恢复探测**：
- 页面从隐藏恢复可见时，对所有已连接联系人立即 `sendPing`（激活 ICE、探测存活）；对 `revivable` 中断开待恢复的连接立即 `scheduleAutoRevive(cId, true)`（300ms 内探测，墓碑恢复后 ICE 可能仍存活，可免交换码恢复）。

**ICE disconnected 温和处理**：
- 旧版 `disconnected` 仅 toast 被动等待。v2.11.0 起 `disconnected` 时主动 `sendPing` 激活 ICE，不清理连接——后台恢复后常短暂进入此态，底层网络未变时 ICE 可自行回到 `connected`；持续无法恢复才 `failed` → `onChannelClose`。

**attemptRevive 温和化**：
- 旧版 `attemptRevive` 见到 ICE 非 `connected`/`completed` 即 `pc.close()` + 删 `revivable`，会误杀后台恢复中暂处 `disconnected` 的连接。v2.11.0 起仅 `closed`/`failed` 才清理 PC；`disconnected` 等保留 `revivable` 供后续重试。

**autoRevive 指数退避重试**：
- 旧版 `scheduleAutoRevive` 单次尝试失败即放弃。v2.11.0 起失败后保留 `revivable` 时按 `autoReviveRetries` 指数退避重试（`base * 1.7^retries`，~3.5s → 6s → 10s → 17s），上限 4 次，覆盖墓碑恢复后 ICE 缓慢回到 `connected` 的窗口；连接成功（`finalizeChannels`）清零计数。`immediate` 参数供 visibilitychange 立即探测。

> 免交换码恢复依赖双方页面均未关闭且底层 PC 存活；若任一方刷新页面（PC 丢失）或网络/IP 真正变更，仍需点「⚡ 重连」重新交换连接码。

## 7. 安全模型

### 7.1 传输安全
DataChannel 强制使用 DTLS。SDP 中的 DTLS 指纹在握手时由浏览器校验，所有数据端到端加密。仅直连模式下流量纯 P2P，不经过任何中转。

### 7.2 信令安全
连接码含 DTLS 指纹与会话凭证。本程序能防**被动窃听**，但**不能单独防主动中间人**：若攻击者能在不可信信道上篡改连接码，可替换为自身码进行转发。缓解措施：
- 通过可信渠道交换连接码；
- 或与对方口头核对一段短指纹（本程序未实现指纹显示，可作为扩展点）。

### 7.3 本地存储
`localStorage` 与导出 JSON 均为**明文落盘**，传输加密不覆盖本机存储。建议妥善保管导出文件。

## 8. 已知限制与扩展方向

| 限制 | 说明 | 可能扩展 |
|------|------|----------|
| 无法自动重连 | SDP 每次临时生成 | 引入轻量信令服务器实现「输入 ID 即连」 |
| 跨 NAT 不同网络无法直连 | STUN 仅获取反射地址，不能穿越对称型 NAT | 需引入 TURN 中继或信令服务器 |
| mDNS 混淆 | Chrome 默认将 host 候选改写为 `*.local`；较新 Chrome 已移除关闭 flag | 已通过 STUN 始终启用 srflx 候选绕过（见 §1.4）；本机真实 IP 被隐藏时显示 STUN 反射地址 |
| 文件不持久化 | 文件/图片内容仅存内存，刷新后下载链接失效，仅保留元数据 | 用 IndexedDB 存储接收到的文件，刷新后可重建下载链接 |
| 无音视频传输 | 仅文本、图片与文件 | 扩展 getUserMedia / MediaRecorder 音视频流 |
| 无群聊 | 仅一对一 | 需引入 mesh 或 SFU 架构 |
| 无指纹核对 | 信令防 MITM 依赖信道可信 | UI 展示 DTLS 指纹供人工核对 |

## 9. 浏览器兼容性

主测 Chrome / Edge（Chromium 内核），兼顾 Firefox。需支持 WebRTC DataChannel、`localStorage`、`RTCPeerConnection.getStats()`、`File.slice().arrayBuffer()`、`CompressionStream`（v2.8.0 连接码压缩，不支持时回退 base64）、`qrcode-generator`/`jsQR`（v2.9.0 二维码）。`file://` 协议下均可运行；剪贴板复制带 `execCommand` 回退以兼容非安全上下文；移动端导出优先 Web Share API（`navigator.share({files})`），不支持时回退 `<a download>`。**二维码摄像头扫描（`getUserMedia`）与系统分享（`navigator.share`）需 HTTPS 或 `localhost` 安全上下文**，`file://` 下可能受限，此时自动降级为上传图片识别 / 保存图片。
