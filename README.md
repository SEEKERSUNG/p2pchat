# 🌍 P2PChat

> 基于 WebRTC 的 IPv6/IPv4 端到端加密 P2P 聊天程序 —— 单个 HTML 文件，打开即用，无需任何后端服务。

> 🌐 **在线体验**：<https://seekersung.github.io/p2pchat/> ｜ 📦 **源码仓库**：<https://github.com/SEEKERSUNG/p2pchat>

## 简介

P2PChat 是一个纯前端的点对点聊天应用。整个程序由三个文件（`index.html` + `css/style.css` + `js/app.js`）组成，双击即可在浏览器中打开使用，不依赖任何服务器、数据库或第三方运行时。两台设备各打开一份，交换一次连接码即可建立加密直连，开始聊天。

消息通过 **WebRTC DataChannel** 传输，使用 **DTLS 端到端加密**，内容不经过任何中转服务器。采用**直连模式 + STUN 辅助**（始终启用，绕过 Chrome mDNS 限制），支持 **IPv6、IPv4 以及局域网**直连。

## 特性

- 🔌 **零部署**：纯静态文件，离线可用，打开即用。
- 🔐 **端到端加密**：WebRTC DataChannel + DTLS，消息与文件内容第三方无法窃听。
- 🌐 **IPv6 / IPv4 / 局域网直连**：默认使用 ICE host 候选 + STUN 反射地址，支持同一局域网或双方均具公网 IP 直连。
- 🧩 **STUN 辅助（始终启用）**：国内公共 STUN 获取 IPv4 反射地址 + Cloudflare / Google STUN 补充 IPv6 反射地址，绕过 Chrome mDNS 混淆；仅建连阶段联系 STUN，消息仍端到端加密。本机真实 IP 被隐藏时，侧栏显示 STUN 反射的公网地址并标注。
- 💬 **联系人管理**：备注名 + 对方用户名、IP、最近联系时间，可编辑/删除/清空记录。
- 📎 **图片 / 视频 / 文件发送**：输入框旁「＋」按钮聚合附件菜单——拍照、图片、视频、录像、文件。图片与视频均支持本地选择或调用相机拍摄（移动端调起后置相机），聊天界面内嵌显示（图片点击页内放大缩放查看，视频内嵌播放器），通过专用 `"file"` DataChannel 分块传输 + 实时进度，不阻塞文字消息，端到端加密。
- 🎤 **语音消息**：输入框左侧话筒按钮按住录音、松手结束，录音后可回放确认再发送或取消；接收方点击内嵌语音气泡收听（圆形播放钮 + 可点击进度条 + 时长）。iOS 端已禁用录音（易致浏览器崩溃），请改用 Edge/Chrome 或电脑端。
- 📱 **二维码连接**：v2.9.0 起邀请码/应答码可生成二维码，支持放大查看、保存本地、调用系统分享到社交 app；接收方可摄像头扫描或上传二维码图片识别，免去手动复制粘贴长连接码。
- ✓ **已读/已送达回执**：消息带序列号（seq），对端收到立即回 ACK，精确判断「✓已送达」；对端打开聊天回「✓已读」。未确认消息自动 3s/6s/12s 指数退避重传，最多 3 次。已读回执在下一个渲染帧即时更新，不再延迟。
- ⏳ **离线消息队列**：断开连接时仍可输入消息，标记「⏳ 未发送」；连接恢复后自动按序发送，无需手动重发。
- ── **消息分界线**：从联系人列表进入聊天时，对方新发来的消息前显示「── 以下为新消息 ──」分界线，方便定位未读。
- 📜 **历史浏览不打扰**：v2.13.6 起上翻查看历史消息时，新消息到达不再强制跳到底部（仅当本就停在底部附近才自动跟随）；自己发送的消息与切换联系人始终定位到最新。
- 💾 **本地持久化**：聊天记录与联系人自动保存到 `localStorage`，并支持导出/导入 JSON 备份（导出文件名含用户名）。
- 📱 **响应式布局**：桌面端双栏，手机端单栏滑入式视图，物理返回键分层拦截（聊天→列表→退出确认）。
- 🔔 **未读提示**：列表显示未读消息红色徽章；移动端返回键不会误退出页面。
- 🧭 **本机地址探测**：侧栏自动展示本机 IPv4 / IPv6 地址。
- ♻️ **断线自动恢复**：网络波动导致 DataChannel 断开时，若底层通道仍存活，自动尝试免交换码恢复。
- 💓 **连接保活与后台恢复**：v2.11.0 起内置 12s 心跳保活防止 NAT 映射超时；iOS 墓碑机制/安卓息屏冻结页面后切回前台时，主动探测连接存活并自动恢复（底层网络未变、双方页面未关时可免交换码恢复）。
- 🆕 **首次引导与账号管理**：首次启动选择新建/导入；设置内可退出账号（退出前提示导出）。

## 快速开始

1. 下载项目文件（`index.html` + `css/` + `js/`），或直接访问在线版：<https://seekersung.github.io/P2PChat/>。
2. 用 Chrome / Edge / Firefox 打开（双击即可）。
3. **首次打开**会弹出引导：选择「🆕 新建账号」或「⬆ 导入备份」恢复历史数据。新建后可查看操作提示（可跳过）。
4. 两台设备（或同一台机器的两个浏览器）各打开一份：
   - **A** 点「➕ 新建连接」→ 复制**邀请码**（或点「📱 二维码」生成扫码图），发给对方。
   - **B** 点「📥 接受连接」→ 粘贴/扫描邀请码 → 生成**应答码**（或二维码），回发给 A。
   - **A** 在第 3 步粘贴/扫描应答码 → 显示「✅ 已建立加密直连」→ 开始聊天。
5. 消息自动保存；刷新页面文字记录仍在；可随时「⬇ 导出」/「⬆ 导入」JSON 备份。连接中点「＋」可发图片/视频/文件，按住「🎤」可录语音。

## 连接方式说明

由于浏览器安全沙箱限制，**无法仅凭输入对方 IP 就直接发起原始连接**，因此采用 **WebRTC + 手动信令**：双方复制粘贴一次连接码完成握手，之后即建立点对点直连。v2.8.0 起连接码经 deflate 压缩，长度缩短约 60%，更易复制粘贴（旧浏览器自动回退未压缩格式，且能识别旧版连接码）。

> ⚠️ **重连说明**：WebRTC 的会话信息（SDP/ICE）每次临时生成、不可复用，因此**已保存的联系人无法凭存储的 IP 自动重连**，每次重新聊天仍需双方**重新交换一次连接码**（断线自动恢复除外）。联系人列表中的 IP / 备注用于识别与整理。这是「纯无服务器」方案的固有代价。

## 直连模式（STUN 辅助始终启用）

本程序始终启用国内公共 STUN 辅助，获取 `srflx` 反射地址绕过 Chrome mDNS 混淆。适用于以下两种场景：

- **同一局域网**：两台设备在同一 LAN（如同一 Wi-Fi / 同一网段）。
- **双方均有公网 IP**：含全局 IPv6（`2000::/3`）或直接分配的公网 IPv4。

> ❌ **跨 NAT 的不同网络（如各自家里的宽带）无法直连**——STUN 仅获取反射地址，不能穿越对称型 NAT，host 候选为内网地址无法在公网路由。

### STUN 辅助说明

- 连接使用国内公共 STUN（小米 `stun.miwifi.com`、腾讯 `stun.qq.com`、B站 `stun.chat.bilibili.com`，并发尝试）获取 IPv4 `srflx` 反射地址，并补充 Cloudflare STUN（`stun.cloudflare.com`，支持 IPv6，国内可达）和 Google STUN（`stun.l.google.com`，候补）获取 IPv6 反射地址，**均不受 mDNS 影响**。
- **IPv6 兜底**：mDNS 同样会隐藏公网 IPv6 的 host 候选；国内 STUN 仅支持 IPv4，故补充 Cloudflare STUN（国内可达）和 Google STUN（候补）提供 IPv6 `srflx`。Google 国内可能不可达，不可达时退回 IPv4 或走 Cloudflare IPv6，不影响连接。
- **仅在建连阶段联系 STUN** 获取反射地址，消息与文件仍走端到端加密的 P2P 直连，**不经过 STUN**。
- **本机地址展示**：当本机真实 IP 被 mDNS 隐藏（仅 `*.local`）时，侧栏「本机地址」面板会显示 STUN 反射的公网地址，并标注「本机真实 IP 被 mDNS 隐藏，以下为 STUN 反射获取的公网地址」。

### 为什么直连模式需要 STUN 辅助

WebRTC 的 ICE 连通依赖「候选」（candidate），主要有三类：

| 候选 | 来源 | 是否受 mDNS 影响 |
|------|------|------------------|
| `host` | 本机网卡真实 IP | **受影响**，被混淆成 `*.local` |
| `srflx` | STUN 服务器反射的地址 | 不受影响，真实可路由 |
| `relay` | TURN 中继 | 不受影响 |

- **有 STUN 时**：即便 host 候选被 mDNS 藏成 `*.local`，ICE 仍能通过 **`srflx` 候选**连通——它由 STUN 服务器返回，与本机 IP 是否暴露无关，所以 mDNS 开着也能连。
- **仅直连（无 STUN）时**：ICE **只剩 `host` 候选**，而它被 mDNS 混淆成 `*.local`。对端发起 mDNS 查询时，在不同子网 / 组播受限 / 不同浏览器实例下常常解析不到 → 连不上。

因此，**移除 STUN 后，关闭 mDNS 混淆是连通的前提条件**，而非可选优化。这也解释了「为什么旧版本开着 mDNS 也能连、改成仅直连后突然连不上」。

### ICE 如何选路

当双方均有多种可连路径（例如本机同时有公网 IPv6、NAT 后的 IPv4），ICE 会**并行尝试所有候选配对，谁先连通就用谁**：

1. 收集所有候选（host v4/v6、STUN srflx v4/v6 等）
2. 按优先级排序：host > srflx；IPv6 略高于 IPv4
3. 两两配对后**并行**发起连通性检查，最先握手成功的 pair 被选定
4. 高优先级路径不通时自动退到下一个

因此连接时用户无需关心选路细节——浏览器 ICE 引擎会自动选出当前网络环境下最快、最可靠的路径。这也意味着有公网 IPv6 时优先走 IPv6 公网直连，IPv6 不通时退到 IPv4 srflx，如果 srflx 也不通则连接失败（此时需要 TURN 中继，本程序不支持）。

### 注意事项

- IPv6 需为**全局地址**（`2000::/3`），`fe80::` 链路本地地址仅在同一局域网有效。
- 系统防火墙需**放行入站 UDP**（给浏览器进程加 UDP 入站规则）。
- Chrome 默认的 **mDNS 混淆**会隐藏真实本地 IP，较新版本 Chrome 可能已移除 `chrome://flags/#enable-webrtc-hide-local-ips-with-mdns` 开关。本程序已**始终启用 STUN 辅助**绕过此限制，无需手动关闭 mDNS；本机真实 IP 被隐藏时侧栏会显示 STUN 反射地址。

## 文件、图片、视频与语音传输

连接建立后，点击输入框旁的「＋」按钮弹出附件菜单：拍照、图片、视频、录像、文件；或按住输入框左侧「🎤」话筒按钮录音。

- **双通道架构**：v2.6 起，文字+控制消息走 `"chat"` DataChannel，文件/图片/视频/语音二进制数据走独立 `"file"` DataChannel，两条 SCTP 流互不阻塞。传输大文件时文字消息不再被卡住。
- **图片**：选择图片后经专用 `"file"` 通道分块传输，接收方聊天界面直接内嵌显示（限高 360px），点击页内放大缩放查看。发送方本地即时预览。支持相机拍照（移动端调起后置相机）。
- **视频**（v2.12.0）：与图片对称，经 `"file"` 通道分块传输，接收方聊天界面内嵌 `<video>` 播放器（受限尺寸，可播放控制）。支持本地选视频或相机录像（移动端调起后置相机；iOS 走系统选择器防闪退）。
- **语音**（v2.13.0）：按住输入框左侧「🎤」话筒按钮录音（`MediaRecorder`），松手后弹确认弹窗可回放、发送或取消；经 `"file"` 通道分块传输，接收方内嵌自定义语音气泡（圆形播放钮 + 可点击进度条 + 时长）。需 HTTPS/localhost 麦克风权限；iOS 端禁用录音（MediaRecorder 进程级崩溃无法兜底）。
- **文件**：任意类型文件，经专用 `"file"` 通道 **分块流式传输**（16KB/块），带实时进度条与百分比。接收完成后生成下载链接，可点击「下载」保存到本地。
- **传输中断保护**：v2.7.6 起，传输过程中通道意外断开时背压等待带 30s 超时与关闭事件兜底，自动退出并标记失败，不再永久卡在「传输中」。v2.10.2 起文件/图片/视频的 `meta`/分块/`end` 全部走同一 `"file"` 通道（同一 SCTP ordered stream），保证结束信号严格在所有分块之后到达，修复公网高延迟下 `end` 抢先到达导致图片残缺（顶部一条/灰色条带）；并加传输串行锁防止并发分块交错。
- **内容不落盘、不持久化**：文件/图片/视频/语音仅内存暂存。刷新页面或关闭后链接失效（卡片标注「已失效」），仅保留文件名/大小记录。如需保留请及时下载，或让对方重发。

> 📌 文件/图片/视频/语音传输仅限双方在线时进行，不支持离线补发。

## 已读与已送达回执

v2.6 起采用**消息序列号（seq）+ ACK 累积确认**机制，比旧版 timestamp 阈值更精确、更可靠：

1. **（空）**：消息已发出，等待对端 ACK
2. **✓已送达**：对端浏览器已收到并回复 `ack`（即时，无需对方操作）。ACK 为累积确认——收到 seq 5 的 ACK 表示 0-5 全部送达
3. **✓已读**：对端已打开你的聊天界面（自动回复 `read` 回执，附带已读到的 seq）

可靠传输保障：
- 消息发送后进入重传队列，**3s → 6s → 12s 指数退避**自动重发，最多 3 次（约 21s 后判定失败）
- 接收方按 seq 去重，弱网重传不会出现重复气泡
- 3 次后仍未确认则显示 ⚠ 发送失败提示
- 所有 `send()` 前检查 `bufferedAmount`（chat 通道 64KB 软上限），防止静默丢弃

回执通过 `"chat"` DataChannel 传输，端到端加密。文字消息按 seq 精确判断「已读/已送达」（v2.7.6），文件/图片/视频/语音消息无 seq、回退时间戳判断。刷新页面后回执状态清除。新版对旧版兼容：旧版无 seq 的消息不返回 ACK，退回旧版 `delivered` timestamp 模式。

> ℹ v2.7.8 修复：重新连接后消息序号从历史最大值继续递增（不再归零），避免重连后新消息被旧已读序号误判为「已读」。v2.13.5 修复：清空聊天记录后重连同样不会序号归零（额外以已读/已送达序号为下界），自发消息不再被误标「已读」。

## 离线消息队列

v2.7 新增，解决"断开连接后无法发送"的痛点：

- **离线也可输入**：断线时输入框保持可用，发送的消息标记为「⏳ 未发送」并持久化到 localStorage（附件/话筒按钮保持可点击，点击时提示需先重连——附件不支持离线发送）
- **连接恢复自动发送**：双方重新建立直连后，排队的离线消息按时间顺序自动通过 `"chat"` 通道发出，对方正常接收
- **消息分界线**：每次从联系人列表进入聊天界面时记录时间戳；回到聊天时，对方在此之后发来的消息前显示「── 以下为新消息 ──」分界线，便于快速定位新内容
- 离线消息刷新后仍保留（persistent），连接上线后才转换状态

## 账号与数据

- **首次启动引导**：检测到本浏览器无数据时，弹出引导选择「新建账号」或「导入备份（JSON）」。
- **退出账号**：设置中点「退出账号」可清除本浏览器数据并回到引导界面。退出前弹出选项，可选择「导出备份后退出」或「不备份直接退出」。
- **导出**：桌面端用 `<a download>` 下载 JSON（文件名含用户名，如 `p2pchat-用户名-20260730.json`）；移动端优先调用系统 **Web Share API** 弹出分享/保存菜单，不可用时回退下载。
- **用户名与备注**：每次连接自动同步对方账号用户名；可自定义备注名，显示为「备注（用户名）」，无备注则只显示用户名。已连接时一方改名会实时同步给对方。
- ⚠ **数据安全**：所有数据仅存于本浏览器。退出账号或清空浏览器缓存前，请务必先导出备份，否则联系人及聊天记录将丢失。

## 安全说明

- ✅ **传输加密**：所有消息经 DTLS 端到端加密，网络中任何中间设备均无法解密。
- ⚠️ **信令安全**：连接码内含 DTLS 指纹与会话凭证，请通过**可信渠道**交换（当面、电话、已加密私聊），以防主动中间人攻击。
- 📌 **本地存储为明文**：聊天记录保存在浏览器 `localStorage` 和导出的 JSON 文件中，属于落盘明文，请妥善保管备份文件。

## 技术栈

纯原生 HTML / CSS / JavaScript，零构建。二维码编解码用本地库 `qrcode-generator`（生成）+ `jsQR`（解析），随项目分发、离线可用。核心 API：WebRTC（`RTCPeerConnection` / `DataChannel`）、`localStorage`、`Blob` / `File` 文件处理、`CompressionStream`（连接码压缩）、`getUserMedia`（二维码扫描、麦克风）、`MediaRecorder`（语音录音）、Web Share API（移动端导出 / 二维码分享）、`history.pushState`（移动端返回键拦截）。

详细设计与实现见 [`doc/技术文档.md`](./doc/技术文档.md)。
